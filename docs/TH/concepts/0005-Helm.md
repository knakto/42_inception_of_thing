# Helm

## Overview

Helm เป็น Package Manager สำหรับ Kubernetes ใช้จัดการการติดตั้ง การกำหนดค่า การอัปเกรด และการถอนการติดตั้ง Applications ภายใน Kubernetes Cluster

Helm รวม Kubernetes Manifests ที่เกี่ยวข้องไว้ในแพ็กเกจที่เรียกว่า **Chart** โดยสามารถกำหนดค่าผ่านไฟล์ `values.yaml` และใช้ Templates สร้าง Kubernetes Manifests ตามค่าที่กำหนด

ตัวอย่างเช่น Application หนึ่งอาจต้องใช้ Deployment, Service, ConfigMap และ Ingress หากจัดการด้วย YAML ทั่วไป ผู้ใช้ต้องดูแลไฟล์เหล่านี้แยกกัน แต่ Helm ช่วยรวม Configuration ที่เกี่ยวข้องไว้ใน Chart เดียวได้

### Why use Helm?

เมื่อ Application มีหลาย Resources หรือมีหลาย Environments เช่น Development, Staging และ Production การคัดลอกและแก้ไข YAML แยกกันอาจทำให้เกิด Configuration ซ้ำซ้อนและผิดพลาดได้ง่าย

Helm ช่วยให้ใช้ Chart เดียวกันกับหลาย Environments โดยเปลี่ยนเฉพาะ Values ที่ต้องการ รวมถึงติดตาม Release Revisions และ Roll Back ไปยัง Revision ก่อนหน้าได้

### Key Features

- **Application Packaging:** รวม Kubernetes Resources ที่เกี่ยวข้องไว้ใน Chart
- **Template Rendering:** สร้าง Kubernetes Manifests จาก Templates และ Values
- **Configuration Management:** ปรับค่าของ Application โดยไม่จำเป็นต้องแก้ไข Template โดยตรง
- **Release Management:** ติดตามการติดตั้งและการเปลี่ยนแปลงของ Chart แต่ละครั้ง
- **Upgrade and Rollback:** อัปเกรด Release และย้อนกลับไปยัง Revision ก่อนหน้า
- **Chart Repositories:** ค้นหาและแบ่งปัน Charts ผ่าน Chart Repositories หรือ OCI Registries
- **Dependency Management:** ประกาศ Dependencies ระหว่าง Charts เพื่อจัดการ Components ที่เกี่ยวข้อง

Helm ไม่ใช่ Container Runtime, Container Image Builder หรือ Kubernetes Cluster Manager โดยตรง หน้าที่ของมันคือจัดการแพ็กเกจและ Release ของ Application โดยอาศัย Kubernetes API

## Architecture & Workflow

### Main Components

#### 1. Helm CLI

Helm CLI เป็น Command-Line Tool ที่ผู้ใช้เรียกจากเครื่องของตนเอง เพื่อสร้าง ทดสอบ ค้นหา ติดตั้ง อัปเกรด และถอนการติดตั้ง Charts

Helm ติดต่อ Kubernetes API Server เพื่อจัดการ Resources ใน Cluster โดยใช้ Configuration และ Credentials จาก Kubernetes Context ที่เลือกไว้

#### 2. Chart

Chart คือแพ็กเกจที่รวบรวมไฟล์สำหรับอธิบายและติดตั้ง Application บน Kubernetes

โครงสร้าง Chart โดยทั่วไป:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── values.schema.json
├── charts/
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── _helpers.tpl
└── .helmignore
```

- `Chart.yaml`: Metadata ของ Chart เช่น ชื่อและเวอร์ชัน
- `values.yaml`: ค่า Configuration เริ่มต้น
- `values.schema.json`: Schema สำหรับตรวจสอบโครงสร้างและชนิดของ Values หากมีการกำหนดไว้
- `charts/`: Dependencies ที่บรรจุอยู่ภายใน Chart
- `templates/`: Templates ที่ใช้สร้าง Kubernetes Manifests
- `_helpers.tpl`: Named Templates ที่สามารถเรียกใช้ซ้ำใน Templates อื่น
- `.helmignore`: ระบุไฟล์ที่ไม่ต้องการรวมเมื่อแพ็กเกจ Chart

Chart อาจมีไฟล์อื่นเพิ่มเติม เช่น `README.md`, `templates/NOTES.txt` และ `crds/` ตามความต้องการของ Application

#### 3. Values

Values คือ Configuration ที่ส่งให้ Templates ใช้สร้าง Manifests

ค่าต่าง ๆ อาจมาจาก:

- `values.yaml` ซึ่งเก็บค่าเริ่มต้นของ Chart
- ไฟล์ Values เพิ่มเติมที่ส่งผ่าน `-f`
- ค่าที่กำหนดผ่าน `--set` ใน Command Line

Values ช่วยให้ใช้ Template ชุดเดียวกันกับหลาย Environments โดยปรับเฉพาะค่า เช่น Image, Replicas, Ports และ Resource Limits

#### 4. Templates

Templates เป็นไฟล์ที่ใช้ Go Template Syntax ร่วมกับ Template Functions เพื่อสร้าง YAML Manifests

ตัวอย่าง:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
```

หาก `values.yaml` กำหนด `replicaCount: 3` Helm จะ Render Template ให้ออกมาเป็น:

```yaml
spec:
  replicas: 3
```

ผลลัพธ์ที่ได้เป็น Kubernetes Manifest ซึ่ง Kubernetes สามารถนำไปใช้สร้างหรือปรับปรุง Resources ได้

#### 5. Release

Release คือ Instance ของ Chart ที่ถูกติดตั้งและติดตามแยกกันใน Cluster

ตัวอย่างเช่น สามารถติดตั้ง Chart `myapp` สองครั้งโดยใช้ชื่อ Release ต่างกัน:

```bash
helm install myapp-dev ./myapp
helm install myapp-test ./myapp
```

ทั้งสอง Release ใช้ Chart เดียวกันได้ แต่มีชื่อและสถานะการติดตั้งแยกจากกัน

Helm เก็บข้อมูล Release ใน Kubernetes โดยค่าเริ่มต้นใช้ Secrets เป็น Storage Backend จึงควรพิจารณาสิทธิ์การเข้าถึงและการจัดเก็บข้อมูลอย่างเหมาะสม

#### 6. Chart Repository and OCI Registry

Chart Repository และ OCI Registry เป็นแหล่งเผยแพร่และแจกจ่าย Charts

- **Chart Repository:** แหล่งเก็บ Charts ที่รองรับรูปแบบ Repository ของ Helm
- **OCI Registry:** Registry ที่จัดเก็บ Helm Charts ในรูปแบบ OCI Artifacts
- **Artifact Hub:** แพลตฟอร์มสำหรับค้นหา Charts จากแหล่งต่าง ๆ

Charts จากแหล่งภายนอกควรตรวจสอบผู้เผยแพร่ เวอร์ชัน Configuration และสิทธิ์ที่ Chart ต้องใช้ก่อนติดตั้ง

### How It Works

1. ผู้ใช้เลือก Chart หรือสร้าง Chart ของตนเอง
2. Helm โหลด Chart และ Configuration Values ที่เกี่ยวข้อง
3. Helm Render Templates ให้กลายเป็น Kubernetes Manifests
4. Helm ติดต่อ Kubernetes API Server เพื่อจัดการ Resources ตามการดำเนินการที่ร้องขอ
5. Kubernetes Controllers จัดการ Desired State ของ Resources ตามปกติ
6. Helm บันทึกสถานะ Release และ Revision สำหรับติดตามการติดตั้งและการเปลี่ยนแปลง
7. ผู้ใช้สามารถ Upgrade, ตรวจสอบสถานะ หรือ Roll Back Release ได้ผ่าน Helm CLI

### Architecture Overview

```text
             User / Helm CLI
                    |
                    v
            Chart + Values
                    |
                    v
             Template Engine
                    |
                    v
          Rendered Kubernetes YAML
                    |
                    v
          Kubernetes API Server
                    |
                    v
          Kubernetes Resources
           /        |        \
          v         v         v
      Deployment  Service  ConfigMap

        Helm Release Metadata
          stored in Cluster
```

แผนผังนี้เป็นภาพรวมเชิงแนวคิด โดย Helm ทำหน้าที่ Render และจัดการ Release ส่วน Kubernetes เป็นผู้ควบคุมการทำงานของ Workloads

## Configuration Reference

### 1. Install Helm

Helm CLI ต้องเชื่อมต่อกับ Kubernetes Cluster ที่ใช้งานได้ โดยติดตั้ง Helm จากช่องทางที่เหมาะสมกับระบบปฏิบัติการ

ตรวจสอบการติดตั้ง:

```bash
helm version
```

ตรวจสอบ Kubernetes Context:

```bash
kubectl config current-context
kubectl get nodes
```

Helm ใช้ Kubernetes Context สำหรับเลือก Cluster และ Credentials ที่จะติดต่อ ดังนั้นควรตรวจสอบ Context ก่อนติดตั้งหรือแก้ไข Resources

### 2. Create a Chart

สร้างโครงสร้าง Chart เริ่มต้น:

```bash
helm create myapp
```

คำสั่งนี้สร้าง Directory `myapp/` พร้อมไฟล์ Templates และ Configuration ตัวอย่าง

ตรวจสอบโครงสร้าง:

```bash
tree myapp
```

### 3. Chart.yaml

`Chart.yaml` ใช้กำหนด Metadata ของ Chart

```yaml
apiVersion: v2
name: myapp
description: A Helm chart for a sample application
type: application
version: 0.1.0
appVersion: "1.0.0"
```

- `apiVersion`: เวอร์ชันของ Chart Metadata Schema
- `name`: ชื่อ Chart
- `description`: คำอธิบาย Chart
- `type`: ประเภท Chart เช่น `application` หรือ `library`
- `version`: เวอร์ชันของ Chart
- `appVersion`: เวอร์ชันของ Application ที่ Chart ใช้งาน

`version` และ `appVersion` เป็นคนละค่า โดย `version` ใช้ติดตามการเปลี่ยนแปลงของ Chart ส่วน `appVersion` ใช้อธิบายเวอร์ชัน Application และไม่ได้บังคับให้ Image Tag ต้องตรงกันโดยอัตโนมัติ

### 4. values.yaml

`values.yaml` เก็บค่าเริ่มต้นที่ Templates ใช้

ตัวอย่าง:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: stable
  pullPolicy: IfNotPresent

containerPort: 80
```

ค่าเหล่านี้สามารถนำไปใช้ใน Templates ผ่าน `.Values`

ตัวอย่างการเปลี่ยน Replicas โดยไม่แก้ไข Template:

```bash
helm upgrade --install myapp ./myapp \
  --set replicaCount=3
```

สำหรับการใช้งานจริง ควรเลือก Image Tag ที่เหมาะสมและควบคุมเวอร์ชันให้ชัดเจน ไม่ควรพึ่งพา Tag ที่เปลี่ยนแปลงได้โดยไม่ตรวจสอบ

### 5. Template Example

ตัวอย่างไฟล์ `templates/deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
  labels:
    app.kubernetes.io/name: {{ .Chart.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: {{ .Values.containerPort }}
```

ตัวแปรสำคัญ:

- `.Values`: อ่าน Configuration จาก Values
- `.Release.Name`: ชื่อ Release ที่ติดตั้ง
- `.Chart.Name`: ชื่อ Chart
- Template Functions: ฟังก์ชันสำหรับแปลงค่า ตรวจสอบเงื่อนไข และจัดรูปแบบผลลัพธ์

ตัวอย่างนี้เป็น Deployment Template ขั้นพื้นฐาน หากสร้าง Chart ตั้งแต่เริ่มต้นด้วยตนเอง ต้องตรวจสอบให้แน่ใจว่าค่า Selector, Labels และโครงสร้าง YAML ถูกต้อง

### 6. Render and Validate Templates

ดู YAML ที่ Helm สร้างโดยไม่ติดตั้งลง Cluster:

```bash
helm template myapp ./myapp
```

ตรวจสอบ Chart:

```bash
helm lint ./myapp
```

ทดลอง Install โดยไม่สร้าง Resources จริง:

```bash
helm install myapp ./myapp \
  --dry-run=client \
  --debug
```

`helm template` ช่วยตรวจสอบผลลัพธ์จาก Template ส่วน Dry Run ช่วยตรวจสอบกระบวนการติดตั้งตามโหมดที่ระบุ แต่ไม่ควรถือว่าเป็นการรับประกันว่า Application จะทำงานได้จริงใน Cluster

### 7. Values for Different Environments

สร้างไฟล์ `values-dev.yaml`:

```yaml
replicaCount: 1

image:
  repository: nginx
  tag: stable
  pullPolicy: IfNotPresent

containerPort: 80
```

และไฟล์ `values-prod.yaml`:

```yaml
replicaCount: 3

image:
  repository: nginx
  tag: stable
  pullPolicy: IfNotPresent

containerPort: 80
```

ใช้ Values คนละชุดกับ Chart เดียวกัน:

```bash
helm upgrade --install myapp-dev ./myapp \
  -f values-dev.yaml

helm upgrade --install myapp-prod ./myapp \
  -f values-prod.yaml
```

ตัวอย่างนี้แสดงการแยก Configuration เท่านั้น ในการใช้งานจริง Development และ Production อาจอยู่คนละ Namespace หรือคนละ Cluster ตามข้อกำหนดด้านความปลอดภัยและการดำเนินงาน

### 8. Chart Dependencies

Chart สามารถประกาศ Dependencies ใน `Chart.yaml` ได้

```yaml
dependencies:
  - name: example-subchart
    version: "1.0.0"
    repository: "https://example.com/charts"
```

ตัวอย่าง Repository ข้างต้นเป็น Placeholder ต้องแทนด้วยแหล่ง Charts และเวอร์ชันที่มีอยู่จริง

จัดการ Dependencies:

```bash
helm dependency update ./myapp
```

คำสั่งนี้ใช้ดาวน์โหลดและปรับ Dependencies ตามที่ประกาศไว้ Chart ที่มี Dependencies อาจต้องจัดการ Version และการเปลี่ยนแปลงของ Subcharts ควบคู่กันด้วย

## Common Workflow

### 1. Find a Chart

ค้นหา Charts บน Artifact Hub:

```bash
helm search hub nginx
```

เพิ่ม Chart Repository:

```bash
helm repo add <repo-name> <repo-url>
helm repo update
```

ค้นหาจาก Repository ที่เพิ่มไว้:

```bash
helm search repo nginx
```

### 2. Install a Chart

ติดตั้ง Chart ที่อยู่ในเครื่อง:

```bash
helm install myapp ./myapp
```

ติดตั้งพร้อมสร้าง Namespace หากยังไม่มี:

```bash
helm install myapp ./myapp \
  --namespace development \
  --create-namespace
```

ติดตั้ง Chart จาก Repository ใช้รูปแบบ:

```bash
helm install <release-name> <repo-name>/<chart-name>
```

### 3. Inspect Releases

แสดง Releases:

```bash
helm list
```

ดูสถานะ Release:

```bash
helm status myapp
```

ดู Configuration Values ที่ใช้:

```bash
helm get values myapp
```

ดู Manifests ที่ Helm จัดการสำหรับ Release:

```bash
helm get manifest myapp
```

เมื่อใช้ Namespace ที่ไม่ใช่ Default ให้ระบุ `-n <namespace>` ในคำสั่งที่เกี่ยวข้อง

### 4. Upgrade a Release

อัปเกรด Release ด้วย Chart หรือ Configuration ใหม่:

```bash
helm upgrade myapp ./myapp \
  --set replicaCount=3
```

ใช้ `helm upgrade --install` เพื่อให้คำสั่งติดตั้งเมื่อ Release ยังไม่มี และอัปเกรดเมื่อมีอยู่แล้ว:

```bash
helm upgrade --install myapp ./myapp \
  --namespace development \
  --create-namespace \
  -f values-dev.yaml
```

### 5. Roll Back a Release

ตรวจสอบประวัติ:

```bash
helm history myapp
```

ย้อนกลับไปยัง Revision ที่ต้องการ:

```bash
helm rollback myapp 1
```

Helm จะสร้าง Revision ใหม่สำหรับการ Rollback การย้อนกลับ Configuration ไม่ได้รับประกันว่าจะย้อนข้อมูลภายนอก เช่น Database Records หรือ Persistent Data ได้ด้วย

### 6. Uninstall a Release

ถอนการติดตั้ง Release:

```bash
helm uninstall myapp
```

หากระบุ Namespace ตอนติดตั้ง ควรระบุ Namespace เดิมตอนถอนการติดตั้งด้วย:

```bash
helm uninstall myapp -n development
```

การถอนการติดตั้งอาจลบ Kubernetes Resources ที่ Chart จัดการอยู่ แต่การคงอยู่ของ Persistent Volumes, External Resources และข้อมูล Application ขึ้นอยู่กับ Configuration และนโยบายของ Resources นั้น ๆ

### Important Notes

- Helm จัดการ Application Packages และ Releases ส่วน Kubernetes ยังคงเป็นผู้ควบคุม Workloads
- Chart Version ไม่ใช่สิ่งเดียวกับ Application Version
- Template ที่ Render ได้ไม่จำเป็นต้องหมายความว่า Resources จะทำงานได้สำเร็จ
- การ Upgrade อาจได้รับผลกระทบจาก Immutable Fields, API Changes และ Dependencies
- ควรตรวจสอบ Chart จากแหล่งภายนอกก่อนติดตั้ง โดยเฉพาะสิทธิ์ที่ Chart ต้องใช้และ Resources ที่จะสร้าง
- หลีกเลี่ยงการเก็บ Secrets ในไฟล์ Values ที่ Commit ลง Git เพราะ Helm อาจเก็บ Configuration ไว้ใน Release Metadata ภายใน Cluster ด้วย
- ควรตรวจสอบผลกระทบก่อน Uninstall หรือ Roll Back โดยเฉพาะ Application ที่มี Persistent Data
