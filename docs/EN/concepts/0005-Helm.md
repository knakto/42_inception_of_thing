# Helm

## Overview

Helm is a package manager for Kubernetes. It manages the installation, configuration, upgrading, and uninstallation of applications running in a Kubernetes cluster.

Helm groups related Kubernetes manifests into a package called a **Chart**. Charts use templates and configuration values, typically defined in `values.yaml`, to generate Kubernetes manifests.

For example, an application may require a Deployment, Service, ConfigMap, and Ingress. Instead of maintaining every YAML file independently, Helm allows the related configuration to be packaged and managed through a single Chart.

### Why use Helm?

When an application contains multiple resources or must run in different environments, such as Development, Staging, and Production, manually copying and editing YAML files can introduce duplication and configuration errors.

Helm allows teams to reuse the same Chart across environments by changing only the required values. It also tracks Release revisions and supports rolling back to previous revisions.

### Key Features

- **Application Packaging:** Groups related Kubernetes resources into a Chart.
- **Template Rendering:** Generates Kubernetes manifests from templates and values.
- **Configuration Management:** Changes application configuration without directly editing templates.
- **Release Management:** Tracks chart installations and changes over time.
- **Upgrade and Rollback:** Upgrades releases and restores previous revisions.
- **Chart Repositories:** Discovers and distributes charts through chart repositories or OCI registries.
- **Dependency Management:** Declares chart dependencies to manage related application components.

Helm is not a container runtime, container image builder, or Kubernetes cluster manager. Its main responsibility is packaging applications and managing their releases through the Kubernetes API.

## Architecture & Workflow

### Main Components

#### 1. Helm CLI

The Helm CLI is a command-line tool used to create, validate, search, install, upgrade, and uninstall charts.

Helm communicates with the Kubernetes API Server to manage resources in a cluster, using the Kubernetes context and credentials selected by the user.

#### 2. Chart

A Chart is a package containing files that describe and configure an application for deployment on Kubernetes.

A typical chart structure looks like this:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── values.schema.json
├── charts/
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── _helpers.tpl
└── .helmignore
```

- `Chart.yaml`: Chart metadata, including its name and version.
- `values.yaml`: Default configuration values.
- `values.schema.json`: An optional schema for validating value structures and types.
- `charts/`: Dependencies packaged within the Chart.
- `templates/`: Templates used to generate Kubernetes manifests.
- `_helpers.tpl`: Reusable named templates.
- `.helmignore`: Files to exclude when packaging the Chart.

A Chart may also include files such as `README.md`, `templates/NOTES.txt`, and `crds/`, depending on the application's requirements.

#### 3. Values

Values are configuration inputs used by templates to generate manifests.

They can come from:

- `values.yaml`, which contains default values.
- Additional values files provided through `-f`.
- Command-line overrides provided through `--set`.

Values make it possible to reuse the same templates across environments while changing settings such as images, replicas, ports, and resource limits.

#### 4. Templates

Templates use Go Template syntax and template functions to generate YAML manifests.

Example:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
```

If `values.yaml` defines `replicaCount: 3`, Helm renders the template as:

```yaml
spec:
  replicas: 3
```

The rendered result is a Kubernetes manifest that Kubernetes can use to create or update resources.

#### 5. Release

A Release is an installation instance of a Chart tracked separately within a cluster.

For example, the same Chart can be installed twice under different release names:

```bash
helm install myapp-dev ./myapp
helm install myapp-test ./myapp
```

Both releases can use the same Chart while maintaining separate names and installation states.

Helm stores release information in Kubernetes. Its default storage backend uses Secrets, so access permissions and data protection must be considered.

#### 6. Chart Repository and OCI Registry

Chart repositories and OCI registries distribute and publish charts.

- **Chart Repository:** A source containing charts in a Helm-compatible repository format.
- **OCI Registry:** A registry that stores Helm charts as OCI artifacts.
- **Artifact Hub:** A platform for discovering charts from different sources.

Review the publisher, version, configuration, and required permissions of external charts before installing them.

### How It Works

1. The user selects an existing Chart or creates a new one.
2. Helm loads the Chart and its configuration values.
3. Helm renders the templates into Kubernetes manifests.
4. Helm communicates with the Kubernetes API Server to manage resources as requested.
5. Kubernetes controllers manage the desired state of the resources as usual.
6. Helm records release state and revisions for tracking installations and changes.
7. The user can upgrade, inspect, or roll back a release through the Helm CLI.

### Architecture Overview

```text
             User / Helm CLI
                    |
                    v
            Chart + Values
                    |
                    v
             Template Engine
                    |
                    v
          Rendered Kubernetes YAML
                    |
                    v
          Kubernetes API Server
                    |
                    v
          Kubernetes Resources
           /        |        \
          v         v         v
      Deployment  Service  ConfigMap

```

This diagram illustrates the overall process. Helm renders manifests and manages releases, while Kubernetes controls workload execution.

## Configuration Reference

### 1. Install Helm

The Helm CLI must be able to connect to a working Kubernetes cluster. Install Helm through a method appropriate for your operating system.

Verify the installation:

```bash
helm version
```

Check the Kubernetes context:

```bash
kubectl config current-context
kubectl get nodes
```

Helm uses the selected Kubernetes context to determine which cluster and credentials to use. Verify the context before installing or modifying resources.

### 2. Create a Chart

Generate a starter chart:

```bash
helm create myapp
```

This creates a `myapp/` directory containing example templates and configuration files.

Inspect the structure:

```bash
tree myapp
```

### 3. Chart.yaml

`Chart.yaml` defines metadata about the Chart.

```yaml
apiVersion: v2
name: myapp
description: A Helm chart for a sample application
type: application
version: 0.1.0
appVersion: "1.0.0"
```

- `apiVersion`: The Chart metadata schema version.
- `name`: The Chart name.
- `description`: A description of the Chart.
- `type`: The Chart type, such as `application` or `library`.
- `version`: The Chart version.
- `appVersion`: The version of the application used by the Chart.

`version` and `appVersion` serve different purposes. `version` tracks changes to the Chart, while `appVersion` describes the application version. Helm does not automatically require the container image tag to match `appVersion`.

### 4. values.yaml

`values.yaml` contains default configuration values used by templates.

Example:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: stable
  pullPolicy: IfNotPresent

containerPort: 80
```

These values can be referenced in templates through `.Values`.

For example, change the replica count without modifying the template:

```bash
helm upgrade --install myapp ./myapp \
  --set replicaCount=3
```

For production deployments, select suitable image tags and control versions explicitly instead of relying on mutable tags without verification.

### 5. Template Example

Example `templates/deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
  labels:
    app.kubernetes.io/name: {{ .Chart.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: {{ .Values.containerPort }}
```

Important template objects:

- `.Values`: Reads configuration from values.
- `.Release.Name`: The name of the installed release.
- `.Chart.Name`: The name of the Chart.
- Template functions: Transform values, evaluate conditions, and format output.

This is a basic Deployment template. When building a Chart manually, ensure that selectors, labels, and YAML structure are valid.

### 6. Render and Validate Templates

Render the generated YAML without installing it into the cluster:

```bash
helm template myapp ./myapp
```

Validate the Chart:

```bash
helm lint ./myapp
```

Perform a dry-run installation:

```bash
helm install myapp ./myapp \
  --dry-run=client \
  --debug
```

`helm template` helps inspect the rendered output. Dry-run commands can validate parts of the installation process, but neither guarantees that the application will run successfully in the actual cluster.

### 7. Values for Different Environments

Create `values-dev.yaml`:

```yaml
replicaCount: 1

image:
  repository: nginx
  tag: stable
  pullPolicy: IfNotPresent

containerPort: 80
```

Create `values-prod.yaml`:

```yaml
replicaCount: 3

image:
  repository: nginx
  tag: stable
  pullPolicy: IfNotPresent

containerPort: 80
```

Use the same Chart with different values:

```bash
helm upgrade --install myapp-dev ./myapp \
  -f values-dev.yaml

helm upgrade --install myapp-prod ./myapp \
  -f values-prod.yaml
```

This example demonstrates configuration separation. In a real environment, Development and Production may use different namespaces or clusters depending on security and operational requirements.

### 8. Chart Dependencies

A Chart can declare dependencies in `Chart.yaml`.

```yaml
dependencies:
  - name: example-subchart
    version: "1.0.0"
    repository: "https://example.com/charts"
```

The repository URL above is a placeholder and must be replaced with an actual chart source and available version.

Manage dependencies:

```bash
helm dependency update ./myapp
```

This command downloads and updates declared dependencies. Charts with dependencies may also require coordinated management of subchart versions and changes.

## Common Workflow

### 1. Find a Chart

Search Artifact Hub:

```bash
helm search hub nginx
```

Add a Chart Repository:

```bash
helm repo add <repo-name> <repo-url>
helm repo update
```

Search repositories that have been added:

```bash
helm search repo nginx
```

### 2. Install a Chart

Install a local Chart:

```bash
helm install myapp ./myapp
```

Install it in a namespace, creating the namespace if necessary:

```bash
helm install myapp ./myapp \
  --namespace development \
  --create-namespace
```

For a Chart from a repository, use:

```bash
helm install <release-name> <repo-name>/<chart-name>
```

### 3. Inspect Releases

List releases:

```bash
helm list
```

Inspect a release:

```bash
helm status myapp
```

View the values used:

```bash
helm get values myapp
```

View the manifests managed by the release:

```bash
helm get manifest myapp
```

When using a non-default namespace, add `-n <namespace>` to the relevant commands.

### 4. Upgrade a Release

Upgrade a release with a new Chart or configuration:

```bash
helm upgrade myapp ./myapp \
  --set replicaCount=3
```

Use `helm upgrade --install` to install a release if it does not exist or upgrade it if it already exists:

```bash
helm upgrade --install myapp ./myapp \
  --namespace development \
  --create-namespace \
  -f values-dev.yaml
```

### 5. Roll Back a Release

Inspect revision history:

```bash
helm history myapp
```

Roll back to a specified revision:

```bash
helm rollback myapp 1
```

Helm creates a new revision for the rollback operation. Reverting application configuration does not automatically revert external data, such as database records or persistent application data.

### 6. Uninstall a Release

Uninstall the release:

```bash
helm uninstall myapp
```

If it was installed into a named namespace, specify the same namespace when uninstalling:

```bash
helm uninstall myapp -n development
```

Uninstalling may remove Kubernetes resources managed by the Chart. The lifecycle of Persistent Volumes, external resources, and application data depends on their configuration and retention policies.

### Important Notes

- Helm manages application packages and releases; Kubernetes remains responsible for workload execution.
- Chart version and application version are different values.
- Successfully rendered templates do not guarantee that the resulting resources will run correctly.
- Upgrades can be affected by immutable fields, API changes, and dependencies.
- Review external charts before installation, particularly their permissions and the resources they create.
- Avoid committing Secrets in values files to Git. Helm may store configuration within release metadata in the cluster.
- Assess the impact of uninstalling or rolling back a release, especially when persistent data is involved.
