# P1 — K3s Provisioning Across Two VMs

## Context

P1 separates the K3s Server and Worker into two VMs. Vagrant manages their lifecycle, while shell provisioners install K3s inside each VM. The Worker needs both the API Server endpoint and the token used to join the cluster; the two nodes also need distinct network identities.

Sources: [`p1/Vagrantfile`](../../../p1/Vagrantfile), [`p1/scripts/server.sh`](../../../p1/scripts/server.sh), [`p1/scripts/worker.sh`](../../../p1/scripts/worker.sh)

## 1. VM Network and Shared Directory

**Source: `p1/Vagrantfile:4–24`**

```ruby
config.vm.define "pnamnilS" do |pnamnilS|
    pnamnilS.vm.hostname = "pnamnilS"
    pnamnilS.vm.network "private_network", ip: "192.168.56.110"
    pnamnilS.vm.provider "virtualbox" do |vb|
        vb.cpus = "2"
        vb.memory = "2048"
    end
    pnamnilS.vm.synced_folder "./confs", "/home/vagrant/confs", create:true
    pnamnilS.vm.provision "shell", path: "./scripts/server.sh"
end

config.vm.define "pnamnilSW" do |pnamnilSW|
    pnamnilSW.vm.hostname = "pnamnilSW"
    pnamnilSW.vm.network "private_network", ip: "192.168.56.111"
    pnamnilSW.vm.provider "virtualbox" do |vb|
        vb.cpus = "1"
        vb.memory = "1024"
    end
    pnamnilSW.vm.synced_folder "./confs", "/home/vagrant/confs", create:true
    pnamnilSW.vm.provision "shell", path: "./scripts/worker.sh"
end
```

`private_network` assigns an IP to each VM. Both `synced_folder` entries mount the same host directory (`./confs`) at `/home/vagrant/confs`, providing the file handoff used by `server.sh` and `worker.sh` without an additional network file-transfer protocol.

Giving both VMs an interface named `eth1` does not make it one physical interface; it means each VM has an interface with that name in its own network namespace. An earlier Git commit is titled `fixed: ip in worker node should bind interface eth1 for rigth communication`, which supports the interpretation that the interface selection was related to inter-node communication. The commit title alone does not prove that every network case was tested ([commit af73b33](https://github.com/lockdoor/42_inception_of_thing/commit/af73b3337b923c8bcd27bfcf0133ed84095badfd)).

## 2. Server Identity and Flannel Interface

**Source: `p1/scripts/server.sh:3–5`**

```bash
curl -sfL https://get.k3s.io | \
    INSTALL_K3S_EXEC="server --node-ip=192.168.56.110 --flannel-iface=eth1" sh -s -
```

`--node-ip` selects this node's IP address in K3s. `--flannel-iface` specifies the interface Flannel uses for node networking. Setting both values separately avoids relying entirely on interface selection inferred from the VM's routing table.

The Worker sets its own IP (`.111`) and its own `eth1` in `worker.sh:9–12`; it must not reuse the Server's node IP.

## 3. Token Handoff and Worker Join

**Source: `p1/scripts/server.sh:13–14`**

```bash
cat /var/lib/rancher/k3s/server/node-token >> /home/vagrant/confs/token
```

**Source: `p1/scripts/worker.sh:3–15`**

```bash
if [ ! -f /home/vagrant/confs/token ]; then
    echo "No token found, please check pnamnilS first"
    exit 1
fi

curl -sfL https://get.k3s.io | K3S_URL=https://192.168.56.110:6443 \
    K3S_TOKEN=$(cat /home/vagrant/confs/token) \
    INSTALL_K3S_EXEC="agent --node-ip=192.168.56.111 --flannel-iface=eth1" sh -s -

rm /home/vagrant/confs/token
```

The Worker needs several distinct values:

- `K3S_URL` is the API Server endpoint the Worker contacts to join (`192.168.56.110:6443`)
- `K3S_TOKEN` is the authentication token read from the shared directory
- `--node-ip` is the Worker's own node identity, not the Server's address
- `--flannel-iface` selects the Worker's interface for Flannel

The `-f` check prevents installation when the token file is absent. It does not verify that the token is valid, that the Server is ready, or that the Worker can reach port 6443.

After installation, the Worker removes `/home/vagrant/confs/token`. Because this is a synced folder, the deletion also affects the shared host directory; it does not remove the token from the K3s Server's own data store.

## 4. Kubeconfig for the Vagrant User

**Source: `p1/scripts/server.sh:7–11`**

```bash
mkdir -p /home/vagrant/.kube
sudo cp /etc/rancher/k3s/k3s.yaml /home/vagrant/.kube/config
sudo chown -R vagrant:vagrant /home/vagrant/.kube
echo 'export KUBECONFIG=/home/vagrant/.kube/config' >> /home/vagrant/.bashrc
```

The provisioner has elevated privileges, so it copies the kubeconfig generated by K3s into the `vagrant` user's home and changes ownership so that user can read it. It then sets `KUBECONFIG` in `.bashrc` so shells loading the file use that configuration path.

`KUBECONFIG` tells `kubectl` where to read its configuration; it does not create or edit Kubernetes resources itself. The script does not modify the `server:` field in the copied file. Before using the config outside this VM, inspect its endpoint because K3s's default kubeconfig commonly points to a loopback address.

## Edge Cases and Limitations

- Appending the token with `>>` can duplicate it if `server.sh` is provisioned repeatedly while the old file remains.
- Checking only for a token file does not validate its format or contents.
- Removing the file from the Worker also removes it from the host-synced directory; the file is not retained for reuse.
- The script writes a file named `token`, but the current `.gitignore` lists `node-token`, not `token`. Do not assume the created token file will be ignored automatically; inspect [`.gitignore`](../../../.gitignore) and never commit credentials.
- The script does not pin `INSTALL_K3S_VERSION`, so the stable-channel version at install time is used rather than a fixed version on every run.
- Adding `KUBECONFIG` to `.bashrc` affects shells that load that file; it does not change the environment of already-running processes.

## Verification

Run these checks after provisioning:

```bash
# On the Server VM
ip -br addr
sudo systemctl status k3s
kubectl get nodes -o wide

# On the Worker VM
ip -br addr
sudo systemctl status k3s-agent
```

Confirm that each node address matches its configured IP and that the nodes reach `Ready` before concluding the join succeeded. Do not expose the full token in logs, screenshots, or public documentation.
